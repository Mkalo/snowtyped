`select(table)` selects every declared column. `select(table, projection)` or `.select(projection)`
selects specific columns and expressions. Projection keys become the exact output aliases.

<Snippet code={firstQuery} />

Builders are immutable. Each call returns a new query, and calling a clause such as `.where()`
again replaces that clause on the new query.

## Expressions

| Category    | Helpers                                                                    |
| ----------- | -------------------------------------------------------------------------- |
| Comparison  | `eq`, `ne`, `gt`, `gte`, `lt`, `lte`                                       |
| Logic       | `and`, `or`, `not`                                                         |
| Nullability | `isNull`, `isNotNull`, `coalesce`                                          |
| Membership  | `inArray`                                                                  |
| Conditional | `caseWhen`                                                                 |
| Text        | `like`, `ilike`, `lower`, `upper`, `concat`, `trim`, `length`, `substring` |
| Arithmetic  | `add`, `sub`, `mul`, `div`                                                 |
| Dates       | `dateTrunc`, `dateAdd`, `dateDiff`, `datePart`                             |
| Conversion  | `cast`                                                                     |
| Aggregates  | `count`, `sum`, `avg`, `min`, `max`                                        |
| Ordering    | `asc`, `desc`, with optional `FIRST`/`LAST` null ordering                  |

Literal values become bind parameters. An empty `inArray` list compiles to a constant false, or
true for a negated membership test.

Every expression carries its SQL type as `dataType`. A comparison accepts a literal of the left
operand's type, or an expression of a comparable SQL type: numeric types with each other, DATE with
timestamps, VARIANT with anything except structured and spatial types, and structured ARRAY, OBJECT,
and MAP values only with structured values. GEOGRAPHY and GEOMETRY cannot be compared at all. TEXT,
DECIMAL, DATE, TIME, and timestamps all decode as `string` but cannot be compared with each other.
`like`, `ilike`, `lower`, and `upper` need TEXT or VARIANT; `sum` needs a numeric type; `min` and
`max` reject ARRAY, OBJECT, VECTOR, structured, and spatial values; `jsonPath` needs VARIANT or a
semi-structured or structured ARRAY or OBJECT; spatial values cannot be GROUP BY, ORDER BY, or
PARTITION BY keys; predicates must be BOOLEAN; and UPDATE, MERGE, and INSERT ... SELECT values
follow the comparison rule. These checks run at compile time and again at runtime. Literals compared
with a `jsonPath` are bound as JSON.

<Snippet code={expressions} />

Arithmetic keeps integer operands as `bigint`, except that integer division yields an exact
decimal; any FLOAT operand yields `number`. Literal operands are bound and cast to the left
operand's domain. `coalesce(value, ...fallbacks)` is non-null when any argument is non-null, and
`caseWhen(predicate, value).when(...).else(value)` is nullable without `.else()`. COALESCE and CASE
values share one SQL type, so TEXT and DATE cannot be mixed, and CASE conditions must be BOOLEAN.
Arithmetic needs numeric types, the string helpers need TEXT, and the date helpers need DATE, TIME,
or timestamp values. `cast(value, type)` converts to any scalar domain except VARIANT and
BINARY (`'decimal'` takes precision and scale) and keeps the input's nullability. The date helpers
take a lowercase date part and reject parts that do not apply to DATE or TIME inputs; adding a time
part to a DATE yields TIMESTAMP_NTZ.

## Joins

Inner, left, right, full, and cross joins are supported. Project joined columns after joining so
they are in scope. Outer joins make the columns of the optional side nullable in the result type.

## Nested objects

A projection entry can be a plain object of further entries, nested to any depth. The SQL stays
flat: each leaf is projected under its dotted path, such as `"customer.name"`, with its own exact
wire format, and rows are rebuilt into objects when they are decoded.

<Snippet code={nested} />

An object over an outer-joined source becomes `null` only when that is certain. Its keys are its
direct entries whose declared type excludes NULL, such as a `.notNull()` column or `count()`. The
object is `null` when every key reads NULL and each key can only be NULL through an outer join.
A present object proves the sources that every key proves, so their other NOT NULL columns are
non-null inside it. Only a column key proves its source; an expression key such as `coalesce()`
can be non-NULL while some of its sources are absent, so it proves none. When an object collapses,
its entries from other sources are dropped with it, so keep those outside the object. An object without keys, or with a key that no outer join can null, is always
an object, with each entry nullable as usual. Include the joined table's NOT NULL key to make an
object collapse.

Nested objects are rebuilt per result row, so a one-to-many join still returns one row per child,
and `.limit()` and `.offset()` count those joined rows; [relations](#relations) load
children per parent instead. Execution, streaming, pools, and
transactions decode nested rows the same way. A query with a nested projection cannot be a derived
table, CTE, set operand, subquery, or INSERT source, and nested paths cannot repeat another
projection alias.

## Relations

`one(table, { from, to })` and `many(table, { from, to })` declare that a parent row has at most
one, or any number of, rows of `table` whose `to` column equals the parent's `from` key. The
optional third argument shapes the related query: project, filter, join, order, or nest further
relations with `withRelations`. `withRelations(query, { name: relation })` adds each relation as a
property of the parent rows: an array for `many`, an object or `null` for `one`.

<Snippet code={relations} />

Loading is predictable. The parent query runs once and keeps its own `.limit()`, `.offset()`,
grouping, and row count; then each relation runs one query per batch of up to 1,000 distinct
parent keys (`{ batchSize }` changes that), as `WHERE to IN (...)` added to the related query's
own filter. Nested relations repeat this per level. `db.execute()` returns every statement's ID in
`queryIds`, parent first. Duplicate parent rows each get the children of their key, and a NULL key
gets `[]` or `null`. A `one` relation that matches several rows for one key throws.

Keys must be INTEGER, DECIMAL, TEXT, or DATE columns or scalar expressions of one shared SQL type;
DECIMAL keys match by value regardless of scale. A key the parent query does not project is added
as a hidden column and removed from the rows, except in DISTINCT queries, which must project it;
grouped queries must group by it. Related queries cannot use `.limit()` or `.offset()`, which would
cut across parents; for a per-parent limit, use `.qualify()` with `rowNumber()` partitioned by the
`to` key.

`db.stream()` reads parents in batches of `batchSize` and loads each batch's children before
yielding it. Statements run on the same connection, inside a transaction when called on its
client. Snowflake isolates each statement separately (READ COMMITTED), so the parent and related
queries can observe changes committed between them, even inside a transaction.

## Grouping and pagination

Use `.groupBy(...)`, `.having(predicate)`, `.orderBy(...)`, `.distinct()`, `.limit(n)`, and
`.offset(n)`.

<Snippet code={grouping} />

Counts decode as `bigint`. Sums decode as exact decimal strings and are nullable, because a sum
over an empty group is NULL. A query with `.groupBy()` or any aggregate rejects
columns that are neither grouping keys nor aggregated, and nested aggregates outside `over()`.
Grouping keys match structurally, so `groupBy(lower(name))` allows `lower(name)` but not `name`.
In a grouped query whose projections are all text, boolean, or binary, a window function in
`.orderBy()` must also be projected. With `.distinct()`, order expressions must be projected.

## Derived tables and CTEs

`.as('name')` turns a query into a derived table, and `.asCte('name')` makes it a CTE source. The
result's `.columns` keep their inferred output types and outer-join nullability. Selecting from or
joining a CTE includes its definition automatically.

## Set operations

`.union()`, `.unionAll()`, `.intersect()`, and `.except()` combine queries whose projections have
the same aliases and SQL types, checked at compile time and at runtime. Branches are aligned by
alias, not position, and the combined columns keep their SQL type.

<Snippet code={setOperations} />

UNION results are nullable when either branch is, INTERSECT results only when both are, and EXCEPT
keeps the left branch's types. Mixed numeric families (integer, decimal, float) or temporal kinds
are rejected; precision and scale within a family widen in Snowflake. Chained calls apply to the
whole preceding query and every operand is parenthesized, so INTERSECT's higher precedence never
regroups a query. Order and paginate a combined query with its own `.columns`. Branch CTEs are
hoisted into one leading WITH, and combined queries also support `.as()` and `.asCte()`.

## Recursive CTEs

`recursiveCte(name, anchor, recursive, options)` compiles
`WITH RECURSIVE name (...) AS (anchor UNION ALL recursive)`. The callback receives `self`, the CTE
as it is being defined, and returns the recursive branch. The result is a CTE table you can select,
join, or combine like any other.

<Snippet code={recursiveCtes} />

The anchor's projection is the row contract: `self` and the result have its types and SQL types.
The recursive branch must produce the same aliases and SQL types, and it cannot add NULLs to a
column unless that column is listed in `nullable`. Snowflake only treats uppercase names (`A-Z`, digits, `_`, `$`) as
recursive, so other names are rejected.

The recursive branch is one SELECT with scalar projections, filters, and joins. It must reference
`self` exactly once in FROM or a join, keep it on the preserved side of outer joins, and place outer
joins after every other join. Aggregates, windows, grouping, DISTINCT, ordering, pagination, and
ASOF joins are rejected, and so is an anchor that reads another recursive CTE. `self` is only valid
inside its own recursive branch. CTEs used by either branch are emitted before the recursive
definition.

Recursion ends only when the recursive branch returns no rows. An outer join that keeps `self` on
its preserved side returns a row for every `self` row, so filter out unmatched rows (for example
with `isNotNull`), or the query runs until the statement timeout.

## Subqueries

`exists`, `notExists`, `scalar`, and `inSubquery` embed a query as an expression. Call
`.correlate(outer)` on the inner query to let it reference a source of the enclosing query. A
correlated query cannot be executed, compiled, or turned into a derived table on its own, and
references to sources that are neither local nor correlated are rejected statically and at runtime.

<Snippet code={subqueries} />

A scalar or `inSubquery` subquery projects exactly one column. Scalar results are always nullable,
because an empty result reads as NULL; an uncorrelated scalar subquery returning several rows fails
at execution. Snowflake only evaluates correlated scalar subqueries that are ungrouped aggregates,
rejects LIMIT and OFFSET in correlated subqueries, and resolves correlations only against the
immediately enclosing query. The builder rejects those forms before execution.

A scalar subquery keeps its column's SQL type, `exists` and `inSubquery` are BOOLEAN, and the
`inSubquery` operand needs an SQL type comparable with the projected column. In a grouped
correlated subquery, columns of the enclosing query count as constants, so they don't need to be
grouping keys.
